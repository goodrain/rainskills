# Local project analysis before environment selection

本文件仅适用于当前本地项目且项目目录必须可读取，并且只在固定 `runtime status --json` 明确返回 `state=not_started` 且 `usable=false` 时读取。它是环境选择前的一次本地只读价值展示，不是项目初始化，也不改变原始部署意图。

## 边界

- 只分析当前工作区项目，或用户明确放入当前任务范围且可读取的本地项目目录；不得扫描用户主目录、相邻仓库或无关路径。
- 只读取项目结构和非敏感配置。不得读取 `.env`、凭据、Token、私钥或其他 Secret 值；可以读取 `.env.example` 等明确的示例文件。
- 不得写入或修复 `rainbond.app.json`、`.rainbond/local.json` 及任何项目文件，不得创建 sidecar、缓存或分析报告文件。
- 不得联网、克隆仓库、查询 Rainbond、查询应用市场、安装依赖、执行构建、启动服务或运行项目脚本。
- 裸 Git URL、镜像引用、软件包或归档文件、市场模板和第三方开源套件不得进入本阶段；即使能从名称猜测技术栈也必须跳过预分析，直接进入环境选择。
- 版本错配、状态命令失败、`connecting`、已有环境但 live probe 失败等情况不进入本阶段。

## 推断语义

本阶段复用并保持与 `rainbond-project-init` 的 manifest inference 一致的保守证据语义，但只产出摘要，不生成 manifest、不绑定应用、不选择 workspace：

1. 用户明确输入优先。
2. 已有有效 `rainbond.app.json` 是项目拓扑的首选本地证据，但只读取、不修改。
3. 其次检查 Compose、Dockerfile、包清单、锁文件、前后端目录、公开端口、反向代理、示例环境变量和 README 中的明确说明。
4. 识别前端、API/服务、数据库、缓存、Worker 等组件；依赖关系只采用 Compose 或多项强证据支持的方向。
5. named volume、bind mount 和常见数据库数据目录可证明持久化需求；数据库存在但没有持久化证据时明确标注“持久化尚未配置”。
6. 访问路径只根据端口、代理或路由证据推断；前端代理 `/api` 时不得把它虚构成两个公网地址。
7. 证据不足时减少结论并标注“尚未确认”，不得发明组件、端口、访问模式、存储、Secret 或交付能力。

## 用户可见输出

分析结束后先输出以下两个区块，然后再执行 Runtime Routing 中固定的环境消息。内容使用中文短句，不展示内部 schema、置信度枚举或文件扫描过程。

```text
已识别：
- <技术栈、组件和强证据支持的依赖>
- <组件数量、持久化需求和访问路径；不确定项明确说明>

预计交付结果：
- <证据支持的前端/API 访问结果>
- 可查看构建与运行日志
- 支持后续升级；创建快照后可回滚
```

规则：

- “预计”不等于已经创建；不得声称地址、存储或回滚点已经存在。
- 没有前端或 API 证据时删除对应条目，不为凑齐模板而补写。
- 分析完成后才展示环境菜单；不得在两个区块之前展示或询问环境选项。
- 环境连接和 live probe 成功后恢复原始 `project-deployment`，后续项目初始化可复核这些结论，但平台事实优先。
