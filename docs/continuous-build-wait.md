# 构建等待与完整部署任务

## 已授权任务的等待策略

`rainbond_wait_for_build_completion(timeout=60)` 的 timeout 是单次服务端只读等待窗口，不是任务整体截止时间。完整部署或明确持续监测请求中，`status=running` 应在当前回合围绕同一 event 继续等待，终态成功后继续健康、业务和交付验证。用户明确要求单次查询、指定预算或取消时遵守该范围。

不要用定时唤醒替代这条正常执行路径，也不要要求用户为每次 60 秒窗口重复输入“继续”。运行中的构建不是配置修复失败，等待不计入配置修复的八分钟或重试预算。

## 超时与写入结果

CLI 在服务端等待窗口外保留15秒传输余量，避免服务端刚结束60秒等待时客户端同时中止请求。输入仍限制为1至60秒；请求仍可取消且有总期限，普通读写调用的超时不变。

只读等待传输失败后保留原event并短暂退避回查；连续三次失败报告真实连接阻塞。不得重放部署/构建写请求，也不得因等待失败创建替代应用或事件。401/403、写入确认和破坏性操作边界保持不变。

宿主命令若返回持久会话句柄，应先等待原句柄退出，再进行下一次只读等待，防止同event并发查询。持续等待是宿主中的受控工具回合，不是无限shell忙循环。

## 维护位置与验证

共享策略源在 `contracts/runtime/cli-base.md`，由 `sync:runtime-contracts` 生成各Skill的runtime-gate。部署、源码与包工作流的等待说明同步保持一致，不能只编辑生成文件或在某个Agent提示词中覆盖旧规则。

回归覆盖：服务端响应稍晚于等待预算时仍能返回；同event先running后success的读取不触发任何部署重放；单次60秒输入上限、取消、未知写入不重放等既有检查继续保留。执行 `npm test` 和 `npm pack --dry-run` 检查代码、契约、生成物及安装包。

若在执行机验证GitHub分支修复，记录确切commit及安装来源，不把未发布的分支构建宣称为新的npm发行版本。通过仓库自带安装器安装Skill与CLI，并核对Multica绑定Skill的持久副本，避免旧workspace副本继续覆盖新运行规则。
