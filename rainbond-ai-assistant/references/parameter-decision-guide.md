# 部署参数决策指南

本指南用于为 ready 模型生成部署参数，或优化运行中的实例。参数预设只能作为待验证候选，不能替代工作负载识别、瓶颈判断和基线实验。

## 决策顺序

1. 将用户目标归一化为一个主要目标和若干硬约束。用户只说“更快”时，先区分首 Token 延迟（TTFT）、生成阶段延迟（TPOT/单请求 decode）、总吞吐或高并发；无法从现有指标判断时，只询问会改变参数选择的最少信息，不直接给出性能参数。
2. 读取模型 metadata、当前实例参数、capabilities、resource capacity 和 monitoring。GPU 额外读取实际 allocation、binding 与 usage；CPU 使用 CPU、内存和架构事实。
3. 识别主要瓶颈：`memory_capacity`、`prefill`、`decode_compute`、`queue_capacity`、`cache_reuse`、`cpu_compute`、`communication`、`multimodal_capacity`、`stability` 或 `unknown`。证据不足时保持 `unknown`。
4. 从下面的矩阵形成一个推荐方案；仅当用户要求比较或存在无法代决的业务取舍时展示备选。每个参数变化都必须绑定证据、预期改善的指标、风险和不采用相关参数的理由。
5. 先验证计算模式、运行时版本、模型兼容、GPU 数量、HAMi allocation、参数冲突和资源上限，再请求创建候选实例。运行中调优继续遵循吞吐调优 reference 的基线与回退流程。

## 需要的工作负载事实

以下是决策证据清单，不是向用户发送的问卷。优先从会话、模型和平台读取；新部署没有负载指标时走启动安全规划，不要求用户提供整套性能指标：

- 请求是在线交互、批处理、embedding/pooling、reward/classification 还是多模态。
- p50/p95 输入与输出 token 数、最大必需上下文，而不是模型宣称的最大上下文。
- 目标并发或 QPS、队列是否持续增长、用户更关注 TTFT 还是完整响应时间。
- 系统提示、RAG 文档或多轮历史的稳定前缀占比；没有重复前缀证据时不假设 Prefix Cache 有收益。
- 可接受的精度/质量损失、成本上限、GPU/CPU 模式和最低可用性要求。
- 当前 tokens/s、平均或分位时延、错误/OOM、GPU/CPU/内存压力。指标 unavailable 时保留缺口。

新部署缺少运行指标时，给出 `startup_safety` 候选，并明确哪些结论必须在真实流量或代表性请求集上复核。不得用通用对话、长文本等用户标签虚构 token 分布或并发。

`startup_safety` 是实例创建门禁，不是用户说“优化”后才执行的性能调优。模型最大上下文不能直接作为 `max_model_len`；应使用用户必需上下文或服务端安全候选。权重大小与显存容量的简单比较不能用于断言显存充足或可部署，还必须计入 KV cache、运行时、多模态开销和 allocation 窗口。用户已指定模型时可以跳过模型推荐，但不能跳过本节的参数决策。

## 从业务场景推导部署参数

先从用户请求和已有会话提取用途、输入形态、响应偏好、同时请求规模及预算约束。用途不清楚时先问一个业务问题，例如“这个模型主要用来做什么？”，再按回答补充会改变方案的最少信息。用户已说明场景时不重复询问；用户明确只想试运行时，以试运行作为场景。`startup_safety` 是场景方案的容量检查，不替代场景理解。

场景理解在确定工作空间并读取平台能力与资源后进行，不与工作空间选择一起发送问卷。以下场景表是内部分析索引，不是向用户展示的平台功能菜单；每项任务仍需验证模型、运行时与当前创建接口的完整支持。GPU/CPU 可用性通过 Tool 查询，用户只需表达业务需求和主动提出的成本或计算方式约束。

接受“几十页文档”“十个人使用”等自然语言描述，记录估算范围和不确定性；不能把人数等同于同时请求数，不能按固定页数比例声称得到精确 token 数。有可用样本和当前宿主支持的分词能力时再测量输入，加上历史、系统提示和输出预算推导上下文。缺少 QPS、token 分位数或压测数据不单独阻塞新部署，但不能虚构业务指标。已有明确上下文、并发、预算或模态要求必须保留，不能为了启动静默缩减。

| 场景 | 只补充影响决策的业务信息 | 参数推导重点 |
|---|---|---|
| 在线问答、客服 | 同时请求规模、首字等待或完整响应偏好、历史长度 | 上下文、并发、batch 联动，避免单纯追求大 batch |
| 知识库问答 | 检索内容长度、稳定提示和文档前缀复用 | 上下文预算、前缀缓存，长输入调度需要时评估分块预填充 |
| 长文档分析 | 文档长度范围、输出长度、同时处理几份 | 上下文与 KV 容量优先，联合约束并发和 batch |
| 批量生成、离线处理 | 数据规模、完成时间、质量与成本约束 | 吞吐、batch、并发及资源预算，以代表性任务验证 |
| 图片、视频理解 | 媒体数量、尺寸或帧数、是否需要混合文本 | 模态上限、编码器开销、上下文和接口可表达性 |
| embedding、分类 | 模型任务、输入长度、在线或离线用途 | 模型兼容的 runner/convert、batch、资源和任务专属验证 |

这些场景是推导方向，不是固定数值预设。由助手结合模型架构、量化、运行时、硬件及资源容量选择参数，不能直接套用页面的稳健/均衡/长上下文配置。向用户展示的是场景分析后选出的方案；只有无法同时满足的业务取舍才需要选择。

在工作记录中逐项覆盖下表，记下候选值、来源、选择理由，以及“显式提交 / 继承已验证默认 / 不适用”。记录用于决策和复核，不要求向用户展开整张表，也不向 Tool 发送 schema 之外的记录字段。

| 参数组 | 决策要求 |
|---|---|
| 上下文、并发、batch | 联合决定 `max_model_len`、`max_num_seqs`、`max_num_batched_tokens`；根据场景需求与容量估算形成候选，并区分估算与实测。调度序列上限不等于长上下文实际并发容量，不机械固定为 1，也不盲用运行时大并发默认值。 |
| GPU / CPU KV cache | GPU 在 `gpu_memory_utilization` 与 `kv_cache_memory_bytes` 中选择适用方式或验证默认；CPU 规划 `cpu_kvcache_space_gb`。GPU 预算以实际 allocation 语义为准，不能把历史实例的比例当作默认。 |
| CPU、内存、共享内存 | GPU 和 CPU 实例都评估 request/limit 与 `shared_memory_gib`，优先使用平台适配候选或已验证默认。字段缺失不表示资源为 0 或无限制；未知默认影响容量判断时继续取证。 |
| 精度、兼容和并行 | 模型兼容且容量允许时保留自动精度、原有量化和适用的默认并行配置；无需为了填满表单显式提交所有 `auto`。改变精度或远程代码执行仍遵循原有质量和授权约束。 |
| 缓存和模态 | 区分继承运行时缓存行为与主动调优，不因缺少缓存命中指标强行关闭默认缓存，也不声称有性能收益。纯文本模型无需添加无关媒体零值；多模态模型使用已知需求或服务端安全媒体上限，不静默禁用用户需要的模态。 |

只使用接口实际返回的能力和默认值证据。当前 capabilities 主要提供运行时、存储、网络与 GPU 分配能力，不等于完整参数支持表或场景安全候选；不得假设存在尚未暴露的预检或参数推荐接口。版本文档只能解释语义，不能覆盖平台定制行为。其他模型或其他版本的历史实例不能单独证明当前默认安全。关键值未确认时先精确读取相关 Tool；不能靠试创建探测默认值。普通 `auto` 的具体实现可留待启动后核对，但容量相关未知值不能以“应该能跑”通过门禁。

读完可用证据仍有决定性缺口时，合并成一个简短的业务问题，例如“这个模型需要处理多长的文档、是否需要图片输入？”，不要求用户选择 KV dtype、batch 或显存比例。可安全代决的参数由助手完成；现有授权和明确的监测偏好继续复用。缺口属于接口能力或资源证据时说明 blocker，不把技术缺口转成用户参数问卷，也不为了少提问猜测资源或业务需求。

## 接口和估算边界

- 参数分别映射到实时创建 Tool 的 `resources`、`dynamic_params` 和顶层 `extra_argv`。接口支持不代表适合当前业务；结构化字段优先，高级参数由助手按场景主动评估，不要求用户知道参数名。
- 当前 Console 创建 Tool 未暴露和透传 `multimodal_params`，而后端将 `--limit-mm-per-prompt` 归为结构化受管参数，不能通过 `extra_argv` 绕过。以实时 Tool definition 复核；若场景必需的媒体边界无法表达，报告接口缺口，不静默禁用模态或提交不存在的字段。只有接口实际补齐后才按新 schema 使用。
- 当前 HAMi 分配估算基于权重、运行时余量和上下文分段预留，并未完整纳入并发、batch、KV dtype 和媒体负载。分配通过不能证明目标场景容量；结合模型元数据估算 KV 与并发，保留误差，创建后用实际 allocation 和启动日志复核。Tool 未提供预创建 allocation 时不得声称已读取，关键安全边界仍无法建立则停止，不以创建探测。
- 估算器采用的默认值与运行时默认值可能不同。显存等容量参数优先显式提交有依据的选定值并核对两侧口径；不要硬编码历史实例比例。CPU/内存字段省略时，当前部署构造不会主动设置对应 request/limit，集群是否另行注入默认值必须有证据，不能宣称后端已自动配齐。

## 目标与参数矩阵

| 目标或证据 | 主要候选 | 启用条件 | 不启用或回退条件 |
|---|---|---|---|
| 启动安全、显存或内存不足 | 实际需要的 `max_model_len`、降低 `max_num_seqs`/`max_num_batched_tokens`；GPU 可评估 `kv_cache_dtype=fp8`、运行时量化或更小模型；CPU 调整 `cpu_kvcache_space_gb` | 资源预检余量不足、OOM、KV cache 初始化失败，且兼容性已验证 | FP8/量化不受硬件或模型支持、质量优先且未完成质量评测 |
| 总吞吐或高并发 | 逐步评估 `max_num_seqs`、`max_num_batched_tokens` | 队列持续存在，GPU/CPU 与内存仍有余量，基线请求集稳定 | 队列为空、资源已饱和、错误/抢占/OOM 增加 |
| 长 Prompt 下 TTFT 偏高 | 评估 Chunked Prefill；并发场景再评估 partial-prefill 参数 | 输入较长且 prefill 阻塞其他请求，当前运行时支持相应参数 | 主要瓶颈是 decode、单请求且没有调度竞争、版本能力未知 |
| 短 Prompt 交互 TTFT 优先 | 降低过大的 batch/concurrency 候选，评估更小模型或更快设备 | TTFT 明确是主要 SLO，排队或大 batch 已被证实是主要等待来源 | 为追求总吞吐继续扩大 batch；把完整响应时间等同于 TTFT |
| 重复系统提示、RAG 或历史前缀 | `prefix_caching=enabled` | 有稳定重复前缀，并能用命中或端到端时延验证 | 前缀变化大、缓存压力导致收益不稳定、缺少代表性验证 |
| 长上下文 | 把 `max_model_len` 设为真实需求，并联动 KV cache、batch 与并发 | p95/p99 token 需求或业务上限明确，容量预检通过 | 只因模型支持更长上下文；提高后破坏目标并发或启动安全 |
| 队列为空但单请求 decode 慢 | 更小/量化模型、更合适的 dtype 或更强设备；参数候选需实测 | 计算饱和且不存在排队或 prefill 阻塞 | 仅增加 batch/concurrency 参数；这通常不改善单请求 decode |
| 单卡放不下模型 | `tensor_parallel_size`，必要时增加 GPU | 多 GPU 拓扑可用，模型或 KV cache 确实无法单卡容纳 | 模型单卡可容纳且目标是最低单请求延迟；通信开销未经验证 |
| 跨节点或不均匀切分 | `pipeline_parallel_size` 与合适的 TP 组合 | 单节点容量不足，或拓扑/互联证据支持 PP | 把 PP 当作默认吞吐开关；GPU 数量与 TP×PP 不匹配 |
| 显存需要精确隔离 | `kv_cache_memory_bytes` | 用户或平台需要明确 KV cache 上限 | 与 `gpu_memory_utilization` 同时设置 |
| HAMi shared | 依据实例 `memory_mib_per_gpu` 调整 `gpu_memory_utilization` 或 KV cache | allocation 已确认是 `hami_shared_auto` | 按物理卡总显存计算；TP 导致 whole-GPU fallback 后仍按切片解释 |
| CPU 实例 | CPU request/limit、内存、`cpu_kvcache_space_gb`，有余量后再调 batch/concurrency | CPU runtime 和模型兼容，内存预检通过 | 使用任何 GPU cache、GPU allocation 或 TP/PP 参数 |
| 质量优先 | 原生/兼容 dtype、`kv_cache_dtype=auto`，避免未经验证的运行时量化 | 用户质量约束高或没有可接受的回归阈值 | 为节省资源默认启用 FP8 KV cache 或运行时量化 |
| 成本或低资源优先 | 更小/量化模型、贴合实际的上下文和并发、兼容时比较 CPU 候选 | 成本约束、质量下限和负载目标明确，并完成容量预检 | 只压缩资源而不验证 SLO、质量和错误率 |
| 稳定性优先或发生抢占/OOM | 降低过激的显存、batch、并发或上下文候选，移除无证据的 `extra_argv` | 错误、OOM、抢占或延迟尾部与当前配置变化相关 | 在不稳定基线上继续叠加多个性能参数 |
| 多模态 | `limit_mm_per_prompt` 与上下文、显存、并发联合限制 | 请求模态和每请求媒体上限明确 | 沿用纯文本 token/并发估算，或开放无限媒体输入 |

`gpu_memory_utilization` 用于按实例可见显存比例自动规划 executor；`kv_cache_memory_bytes` 用于显式控制每 GPU KV cache，二者互斥。提高显存利用率只在 allocation 窗口仍有安全余量时作为容量候选，不能直接声称提高 tokens/s。

## 结构化参数的角色

- `runner`、`convert`、`model_impl`、`trust_remote_code` 主要解决任务类型或模型兼容，不是通用性能开关。只有模型 metadata、任务类型或稳定错误要求时才改变；`trust_remote_code` 还需要用户明确接受远程模型代码风险。
- `dtype`、`runtime_quantization`、模型量化和 `kv_cache_dtype` 同时影响兼容性、容量、速度与质量。先检查 capabilities 和模型 metadata，再用代表性质量集验证。
- `max_model_len`、`max_num_seqs`、`max_num_batched_tokens` 和 KV cache 是耦合参数。不得分别最大化；建议必须说明目标上下文下的预期并发与内存风险。
- `tensor_parallel_size` 与 `pipeline_parallel_size` 受 GPU 数量、节点拓扑和 provider 约束。创建后重新读取实际 allocation；HAMi whole-GPU fallback 必须更新资源解释。
- `prefix_caching` 的依据是重复前缀，不是“对话模型”标签。

## `extra_argv` 候选

仅在结构化字段不能表达且当前 runtime capabilities 或版本文档确认支持时考虑：

- Chunked Prefill：长输入与并发请求存在 prefill 调度竞争时。
- partial-prefill 参数：Chunked Prefill 已适用且需要进一步约束并发长 prefill 时。
- CPU offload：模型无法装入 GPU、CPU 内存与互联允许且用户优先“可运行”时；它会增加 CPU-GPU 传输，不是 tokens/s 优化。
- 其他版本相关参数：必须有明确场景需求或已观测瓶颈，以及验证目标，不能因为参数存在就启用。

形成 `extra_argv` 候选后再读取 advanced arguments reference，检查平台保留、结构化冲突、互斥和安全规则。runtime 版本或参数支持未知时不提交，改为 `missing_evidence`。

参数值必须从当前值、服务端能力、容量边界和代表性实验推导。没有这些事实时只描述调整方向或保守起点，不编造通用“最佳值”，也不把某个历史实例的数值固化为 profile 默认值。

## 不应给出参数变化的情况

- 用户目标含糊且不同解释会导向相反参数，例如只说“延迟低”。
- 没有代表性负载，且用户要求的是已运行实例的确定性优化结论。
- 指标 unavailable，无法区分排队、prefill、decode、内存或通信瓶颈。
- 当前错误属于模型不兼容、镜像、调度、挂载、健康检查或注册失败；先走部署诊断，不用性能参数掩盖故障。
- 已有基线显示候选没有改善目标指标，或错误率、质量、OOM、资源争用明显恶化。

## 建议结果

结果必须包含主要目标、瓶颈、事实、缺失证据、逐项参数变化、明确拒绝的候选、预期影响、风险、置信度和验证计划。逐项变化至少说明：参数名、动作、依据、目标指标；已运行实例还应说明当前值和候选值。若结论是“不改参数”，仍需解释瓶颈为何更可能位于模型、硬件或请求模式。
